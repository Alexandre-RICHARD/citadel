## Points problématiques rencontrés en écrivant les tests E2E

Rien n'a été corrigé dans le code du site : chaque point est noté tel que constaté. Les tests concernés sont indiqués.

### Comportements de l'application à examiner

- **P1 : lien d'un mail ouvert dans un nouvel onglet, la page demandée est perdue** (test A1). Après « Plus tard » de l'étape « Protège ton compte », l'onglet du lien atterrit sur `/auth/profile`, alors que `scenarios.md` attend `/backlog`. La page demandée au départ est gardée dans le `sessionStorage` de l'onglet d'origine (`useAuthRedirect`) : le nouvel onglet ouvert par le lien n'en sait rien. Même comportement attendu pour tout lien de mail (connexion par lien, mot de passe oublié). Le test A1 vérifie donc le profil. Quand le code est tapé dans l'onglet d'origine (A2), on revient bien à `/backlog`.
- **P2 : « Confirmer » cliqué trop vite envoie au mauvais endroit** (flaky vu 2 fois, sur B1 et G5, avant l'attente ajoutée dans `openMailLink`). Sur `/auth/verify`, `VerifyPage` lit le type du parcours en cours (`useFlow`) au moment du clic : si `GET /auth/flow` n'a pas encore répondu, il est inconnu, et une inscription confirmée mène au profil au lieu de « Protège ton compte ». Un humain ne clique pas avant la fin du chargement, mais un clic rapide suffit à reproduire. Les tests attendent désormais la fin des requêtes (`openMailLink`).
- **P3 : après un échec, le premier nouvel essai « mange » un 429 sans rien dire** (E2, E6, E7, G2, G10). Un mauvais mot de passe ou un mauvais code ne fait pas attendre le bouton : un nouvel essai dans les 2 secondes reçoit un `429`, et l'interface n'affiche alors que le compte à rebours « Patiente n s » sur le bouton, sans message : l'utilisateur ne sait pas si son essai a été jugé. Appliquer le délai côté interface dès la réponse en échec (comme après un 429) éviterait ce faux départ. Les tests contournent par `retryUntilAnswered`.
- **P4 : nom du fichier des codes de secours en date UTC** (E1, vérifié seulement au format). `buildRecoveryCodesFileName` utilise `toISOString()` : entre minuit et 1 h ou 2 h (heure de Paris) le fichier porte la date de la veille. Sans conséquence grave.
- **P5 : le mail « adresse déjà utilisée » contient un lien** (G3). `scenarios.md` dit « sans lien ni code » ; le mail contient un lien vers `/auth/login` (pas un lien de confirmation, ni jeton). Le test vérifie l'absence de `/auth/verify` et de code. À trancher : le scénario ou le mail.
- **P6 : `-g` ne filtre pas avec la commande du README** (outillage). `pnpm test-e2e -- -g "A1"` passe `-g` après `--` à Playwright, qui le prend pour un filtre de fichiers : tous les tests tournent. Tapé sans `--` (`pnpm test-e2e -g "A1"`) ou via `pnpm exec playwright test --project=chromium -g "A1"`, ça filtre. Le README est corrigé.

### Limites des tests écrits

- **`citadel.localhost` ne se résout pas côté Node sous Windows** (`getaddrinfo ENOTFOUND`) : `page.request` / `request.newContext` de Playwright ne peuvent pas appeler l'API. Les appels directs passent par un `fetch` dans la page (`helpers/api/callApi.ts`), qui envoie aussi l'`Origin` du site (donc le test passe par la protection CSRF comme le front).
- **Chromium headless ne prévient jamais un onglet qu'il revient au premier plan** : `returnToTab` envoie lui-même `visibilitychange` (B2).
- **Les limites par IP et le `429` de connexion** : `compose.e2e.yml` relève les limites par IP, mais pas le délai entre deux échecs d'un même compte (C3, E2…) : ils restent ceux de la prod.
- **Pas d'accès à la base** : « aucune ligne `auth_user` avant la confirmation » (A1) est vérifié par un refus de connexion ; « aucune donnée restante » (G10) par un nouveau compte qui réutilise l'adresse et le pseudo et trouve un GDC vide.
- **Parties de scénario non couvertes** : A8 (interrupteur `AUTH_REGISTRATION_ENABLED`) ; E3, le cas « choix absent s'il n'y a qu'une méthode » (un compte a toujours ses codes de secours en plus d'un facteur) ; G5, la troncature du user agent à 255 caractères (invisible à l'écran) et « boutons inactifs pendant une action » (trop bref) ; L6, l'accusé en échec (il faut un faux Brevo en panne à la demande) ; L7, « le message du champ piège ne compte pas dans la limite » (la limite du contact est relevée en e2e).
